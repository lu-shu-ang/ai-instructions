# 飞书技术文档规范

## 一、先写清执行主体

技术文档中的每个关键动作必须能直接看出执行主体。标题、流程步骤、代码块标题和表格说明都按“主体 + 动作 + 对象或目的”表达，避免只写“加载、查询、同步、校验、下发”等无主语的动作。

例如：

| 不清晰 | 清晰 |
| --- | --- |
| 启动时加载 JWT 密钥 | Browser Network API 启动时加载 JWT 私钥和公钥 |
| 白名单缓存何时加载 | PoP 服务何时从 API 加载全局白名单缓存 |
| 验签代码 | PoP 服务使用缓存公钥验签 JWT |

涉及多个服务的链路，在主流程图后补充“主体职责速览”表，至少写清浏览器或客户端、网关、业务 API、数据库或缓存、边缘代理等主体分别“负责什么”和“不负责什么”。

## 二、流程图按独立链路拆分

一张流程图只解释一个核心问题。不要把定时同步、请求热路径、版本判断、异常降级等互不同时发生的链路混在同一张图中；需要时拆成两张或多张小图，并用图注说明各自的适用时机。

图中的请求方向必须体现真实调用方：数据库是被动数据源，不能画成数据库主动触发 HTTP 接口。应明确表现“调用服务 → 被调用服务 → 数据库查询 → 响应返回”的方向。

对于同步或缓存流程，优先拆分为：

1. **同步图**：触发者、请求 API、API 查询数据源、响应后的版本或错误分支；分支必须是同一次处理中的互斥结果。
2. **热路径图**：单次业务请求读取哪一层缓存、命中和未命中的结果；若热路径不查询 API 或数据库，在图注中明确说明。

写入飞书前先渲染预览并检查：箭头方向、主体、条件分支和图注是否让读者能在不阅读代码的情况下理解主线；写入后再导出实际画板预览复核。
