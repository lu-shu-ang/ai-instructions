# SPEC：迁移兼容性审查

## 适用范围

本规则适用于新增或变更持久化数据、缓存、Token/凭证字段、接口请求响应、服务间协议、权限规则或
有状态任务的需求规格与技术方案。目标是避免只设计目标稳态，而遗漏新旧版本、旧数据和旧凭证在
发布期间共存的迁移过程。

## 必经审查

在完成 SPEC 或技术方案前，必须明确回答：

1. 哪些旧客户端、旧服务实例、旧缓存、旧数据或旧凭证仍可能存活？
2. 每类存量的最长存活时间是多少；能否主动刷新、吊销、迁移或回滚？
3. 发布期间哪些新旧版本会同时运行？
4. 兼容期内应优先保证不断流，还是优先立即收紧权限？该取舍是否已由需求方确认？
5. 兼容期的开始条件、结束条件、可观测指标和异常处理分别是什么？
6. 回滚到旧版本时，新增数据、缓存和协议字段是否仍可被安全处理？

若任一问题无答案，规格必须标记为待澄清，不能把最终稳态规则直接当作上线即刻规则。

## 迁移矩阵

涉及版本化输入或状态时，规格必须列出新旧组合的迁移矩阵，至少包含：

| 输入/状态版本 | 消费方版本 | 兼容期行为 | 退出条件 |
|---|---|---|---|
| 旧 | 新 | 明确兼容、拒绝或受限降级策略 | 明确时间、迁移完成或指标条件 |
| 新 | 新 | 目标稳态行为 | 长期 |
| 新 | 旧 | 发布顺序或回滚行为 | 旧消费者下线或回滚结束 |

“兼容”必须写清其安全边界，不能只写“兼容旧版本”。

## 权限与缓存变更的额外要求

当变更影响鉴权、授权或放行规则时，必须分别说明：

- 存量凭证缺少新增字段时如何处理；
- 新系统产生但字段无效/缺失的输入如何处理；
- 缓存失联、陈旧或迁移中版本不一致时，继续服务、拒绝还是降级的条件；
- 兼容期是否会暂时保留旧权限，以及风险接受者和结束条件。

## 通用示例

为 Token 新增一个决定访问范围的受签名字段时，不能在新消费者上线的同一刻无条件拒绝所有缺少
该字段的 Token：旧客户端可能仍持有有效 Token。规格应定义先让签发方产生新字段、再部署可识别
新旧 Token 的消费者、等待旧 Token 最大有效期或完成主动刷新/吊销、以监控指标确认旧 Token 清零，
最后才进入严格拒绝模式。若必须立刻收紧某一主体的权限，则应明确其旧 Token 的吊销或强制刷新
流程，而不是依赖自然过期。
