
请你以“资深业务分析师 + 能把复杂业务讲明白的老师”的方式帮助我梳理项目。

我的目标不是只得到一份模块、字段和公式清单，而是让我能够快速理解：

1. 这个业务为什么这样设计；
2. 每个概念解决什么问题；
3. 数据是从哪里产生的；
4. 数据经过哪些步骤；
5. 最终影响了谁、产生了什么结果；
6. 后续应该怎样设计数据库表。

请遵守以下表达要求：

一、先讲业务全貌

先用一段通俗的话说明整个业务发生了什么，再展开模块、流程、公式和数据库设计。
不要一开始就直接罗列字段、公式或表名。

二、每次引入新概念时，必须依次说明

1. 这个概念是什么；
2. 谁产生这个数据；
3. 为什么需要这个概念；
4. 它想解决什么业务问题；
5. 它参与哪一步计算或流程；
6. 它最终影响什么结果。

例如不能只写“进步系数 = 本月分数与上月分数的差值”，还要解释为什么需要和上月比较，以及它是怎样奖励进步、反映退步的。

三、遇到相似概念时必须进行对比

如果出现两个容易混淆的概念，请用表格说明：

- 两者分别是什么；
- 由谁产生；
- 评价对象是什么；
- 使用场景是什么；
- 为什么不能合并；
- 最终影响什么。

四、使用一个连续的复杂案例贯穿整个过程

不要每讲一个公式就换一套数据。

案例数据必须能够让所有重要公式真正发挥作用，不能把关键数据都设置成相同值。

案例中至少包含：

- 一个明显进步的对象；
- 一个小幅进步的对象；
- 一个发生退步的对象；
- 两类评分或数据存在差异；
- 一个达到资格线的对象；
- 一个未达到资格线的对象；
- 一个正常结果；
- 一个异常或边界结果。

如果某个公式因为示例数据相同而始终等于0，请重新设计示例数据。

五、讲公式时使用真实业务名称

不要使用原代码中的函数名或变量名。

每个公式都要按照以下格式说明：

- 公式计算的业务目的；
- 公式中的每个数字来自哪里；
- 完整计算过程；
- 中间结果；
- 对下一步造成的影响；
- 分母为零、数据缺失或结果为负时如何处理。

六、展示完整的数据流转

使用同一个案例展示：

原始业务数据
→ 中间统计结果
→ 全局结果
→ 分组结果
→ 个人结果
→ 业务流水
→ 账户或最终状态

不要只给最终结果，必须保留关键中间结果，让我能够核对每一步。

七、最后落到一个具体对象

最后选择一个具体会员、订单、商品、客户或其他业务对象，完整说明：

- 它参与了哪些流程；
- 它获得了哪些结果；
- 每一个结果为什么产生；
- 最终生成了哪些数据库记录；
- 最终余额或状态是什么。

八、说明数据库怎样承接业务

每讲完一个关键步骤，都要说明：

- 输入来自哪张表；
- 使用哪些关键字段；
- 中间结果保存在哪张表；
